**CampusLink Google sign-in — 25 October 2026**

CampusLink no longer requires the legacy Neon user's local `emailVerified` flag for the first application-side Google association. A callback must still prove the exact existing canonical Neon subject, the identical academic email, strict raw and normalized Google verification, an authoritative Google Workspace `hd` matching `usmba.ac.ma`, and no conflicting Google binding. Account status, roles, study details and password state are preserved. This does not merge different Neon subjects by email or rewrite Neon's local verification flag.

The regression suite covers direct association with `emailVerified:false`, refusal of a string Google verification flag, absent or mismatched Workspace proof, conflicting subjects, disabled/deleted users and revoked sessions. Its provider is simulated; this does not prove that an unverified legacy user can pass Managed Neon's earlier OAuth gate.

Validation: `node --test tests/backend-google-oauth.test.mjs` completed with **57 passed, 0 failed, 0 skipped** using the separate `.env.oauth-test.local` database and disposable `campuslink_test_*` schemas. No real email, Google sign-in or provider-account mutation occurred. Runtime: approximately 12 minutes 25 seconds over the remote test database.

**Managed Neon limitation.** The saved real test on 24 October received `account_not_linked` before Neon supplied a verifier, session or Google identity for an unverified legacy credential user. The application cannot safely infer ownership from that error. Current Better Auth 1.7.6 source defaults `account.accountLinking.requireLocalEmailVerified` to true independently of `trustedProviders`; its type documentation marks the option for removal. Current published Neon management APIs expose neither this setting nor a custom linking hook. OAuth provider PATCH accepts client credentials and the Microsoft tenant only; auth config PATCH changes the application name.

Consequently this local fix removes the redundant CampusLink gate but cannot promise Google-only first use for accounts blocked upstream. A complete direct flow needs a supported provider capability or a separately designed Google OIDC/session integration using an owned OAuth client, verified signature/issuer/audience/expiry/nonce and exact Workspace domain, conflict handling and safe recovery of legacy credentials/sessions. Bulk marking emails verified, trusting an error callback, or adding an unsupported Neon PATCH property is not a valid implementation.
