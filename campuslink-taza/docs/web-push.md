# Notifications sur les appareils

Les étudiants activent chaque appareil dans **Profil → Préférences de notifications**. Aucun dialogue système ne s’ouvre automatiquement. Les préférences `questions`, `resources` et `mentions` contrôlent respectivement les nouvelles questions de la filière, ses documents et les réponses destinées à l’étudiant. Les conversations générales ordinaires restent silencieuses.

Le serveur utilise Web Push et VAPID, sans compte Firebase. Après la migration `038_web_push.sql`, configurer les variables serveur de `.env.example` : `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_PRIVATE_KEY`, `WEB_PUSH_SUBJECT` et `CRON_SECRET`. Générer une paire avec `web-push.generateVAPIDKeys()` une seule fois par environnement ; conserver la clé privée dans un secret serveur, sans préfixe `VITE_`. La configuration publique expose uniquement la clé publique. Le sujet doit être une URL HTTPS ou une adresse `mailto:` valide.

Les notifications et les tâches d’envoi sont enregistrées dans la même transaction PostgreSQL. Les tâches ne deviennent visibles qu’après sa validation, y compris pour les dépôts de fichiers par morceaux. `waitUntil` conserve l’invocation Vercel pendant l’envoi sans ralentir la réponse du dépôt. Un verrou par appareil empêche deux workers d’envoyer simultanément vers un abonnement révoqué ; les autres appareils sont traités en parallèle. Les erreurs temporaires sont réessayées avec un délai, les réponses 404/410 révoquent l’abonnement. Les événements déjà lus, supprimés, hors périmètre ou interdits par les préférences sont ignorés après vérification de l’état actuel.

Les publications et les requêtes actives réveillent le traitement, au plus 200 tâches par passage et 40 secondes de budget. Le cron quotidien `/api/push/dispatch` est une récupération supplémentaire protégée par `Authorization: Bearer CRON_SECRET`. Les tâches restantes et les réessais attendent le prochain réveil ; ce cron quotidien ne garantit pas un réessai immédiat sans trafic. Les tâches expirent au bout de 24 heures et les résultats terminés sont nettoyés après sept jours. Pour une audience nettement plus grande, prévoir un ordonnanceur fréquent ou une file durable externe.

Le service worker reçoit les messages même sans page ouverte. Il vérifie l’association locale de l’appareil, affiche une notification système et ouvre uniquement un identifiant de notification interne. Après connexion, l’API retrouve la notification du destinataire et vérifie sa destination. La réception seule ne marque rien comme lu. L’ouverture utilise le parcours existant ; la conservation après première lecture reste de 72 heures.

HTTPS est nécessaire hors localhost. Sur iPhone/iPad, utiliser iOS/iPadOS 16.4 ou plus récent et installer l’application sur l’écran d’accueil. L’autorisation et la livraison dépendent du navigateur, des réglages du système et du réseau. La déconnexion désactive localement cet appareil avant de fermer la session ; un changement de compte n’hérite jamais silencieusement de son abonnement.

Les tests utilisent des schémas PostgreSQL jetables, un transport injecté et des API navigateur simulées. Ils n’envoient aucun message réel et ne sollicitent aucune autorisation système.
